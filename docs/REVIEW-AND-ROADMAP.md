# Habits_ — Полное ревью и дорожная карта

> Проект: React Native / Expo Android-приложение для трекинга привычек.
> Стек: Expo SDK 53, React 19, React Native 0.79, AsyncStorage, expo-notifications.
> Ветка: `claude/check-habits-repos-6UFGe`
> Дата ревью: 2026-07-12

---

## 1. Что это за приложение (реконструкция замысла)

Ежедневный трекер привычек трёх типов:

1. **boolean** — сделал/не сделал (стакан воды утром)
2. **number** (в коде также встречается `quantitative` — это баг) — количественная (отжимания × 20, чтение × 30 мин)
3. **weight** — трекинг веса с целевым значением

Поверх этого:
- **Серии (streaks)** — сколько подряд дней выполняется привычка.
- **Статистика** по неделе / месяцу / году.
- **Достижения** (7 предустановленных, часть логики закомментирована).
- **Архив** — завершённые привычки перемещаются, можно восстановить с суммированием прошлой статистики.
- **Push-уведомления** (заявлены, но по issue #13 не работают вообще).
- **Темы** (blue, purple; в UI показывается 5 — заглушки).
- **Настройки**, экспорт прогресса через `Share`.

### Данные

- **Всё локально**, `AsyncStorage`. Никакого облака, синхронизации, аутентификации.

### Что стоило бы починить в архитектуре в первую очередь

1. Перенести всё в `src/` c подпапками (`screens/`, `components/`, `services/`, `utils/`, `constants/`).
2. Удалить `HomeScreen.js` и `settingsStorage.js` (не используются).
3. Ввести единый модуль `habitStore` (Zustand / Redux Toolkit / self-rolled context) — сейчас 700-строчный `App.js` тянет весь state.
4. Ввести абстракцию `completionOf(habit, date) → {isDone, value, meta}` и использовать её везде вместо 5 разных inline-веток.
5. TypeScript. Проект без типов при таком количестве union-типов и полей — мина.

## 3. Ревью с 4 перспектив

### 3.1 Как продакт-менеджер

**Ценность продукта:** привычки — конкурентная ниша (Habitica, Loop, Streaks, Fabulous). Отличаться можно только либо (а) простотой и красотой, либо (б) уникальными фичами. Здесь фич много, но они разрозненны — нет цельной истории, нет метрики удержания, нет вирусного крючка.

**Что цепляет уже сейчас:**
- Трекинг веса встроен в трекер привычек — редкая комбинация, полезная.
- Три типа привычек — достаточно гибко.
- Архив с суммированием статистики — необычная и приятная механика.

**Что ломает продукт:**
- Уведомления не работают (issue #13) — трекер без напоминаний бесполезен.
- Форма создания привычки не доделана (issue #21) — новый пользователь застревает на 5-й секунде.
- Дни недели не учитываются в плане (issue #17) — пользователь ставит цель "3 раза в неделю", а прогресс считается от 7 дней.
- Нет срока привычки (issue #16) — нельзя ставить челленджи на 30 дней.
- Нет описания дня (issue #19, #20) — обещанное "размышление о прогрессе" на уровне PRD, в коде — нет.

**Метрики, которые нужно ввести (не в этом MVP, но в следующем цикле):**
- Day-1 retention после создания первой привычки.
- % завершения первой привычки за 7 дней.
- Число активных привычек на пользователя (сейчас нет ограничения — 100 в `settingsStorage.VALIDATION`, но не применяется).

**Вердикт PM:** проект жив на 5/10. Есть скелет, но пользователь уходит на 3-й минуте.

### 3.2 Как дизайнер

**Что хорошо:**
- Единая система токенов (`SPACING`, `BORDER_RADIUS`, `TYPOGRAPHY`) — обычно у начинающих проектов её нет.
- Тёмная тема из коробки.
- Иконки Ionicons — консистентно.
- Карточки с прогрессом-заливкой (background progress) — приятное решение.

**Что плохо:**
- **Всего 2 темы (blue, purple)**, а в `SettingsScreen.getThemeDescription` захардкожены описания для 5. Пользователь видит 2 варианта — визуально бедно.
- Splash-экран сделан текстом "✓" в круге — выглядит как MVP-заглушка.
- `TYPOGRAPHY.h1` = 32px, `h2` = 28px — при таком крупном заголовке в мобильном UI слишком тяжело; редко где применяется.
- Отсутствует система motion (нет `Easing`, нет `LayoutAnimation`).
- Пустые состояния бедные: одна эмодзи + текст. Нет иллюстраций.
- Нет фигуры бренда (нет своего логотипа, только галочка).
- `Alert.alert` используется как основной способ обратной связи — на 2026 год это неприемлемо, нужны toast-и / bottom sheet.
- Долгое нажатие для меню действий (`onLongPress` 500ms) — не обнаруживаемо; никакого onboarding-хинта.
- Header при переходе в архив полностью меняется, но `MainApp` из-за этого разрывает tab bar. Плохой UX-паттерн.

**Что нужно (минимум для 10/10):**
- Design system с 4-5 темами + accent-цветами; переход на dynamic color на Android 12+.
- Motion-палитра (durations, easings, presets: fade, slide, scale).
- Настоящие иллюстрации для empty states (SVG).
- Замена `Alert` на toast (готовые: `react-native-toast-message`) и bottom-sheet (`@gorhom/bottom-sheet`).
- Хаптик (`expo-haptics`) на ключевых действиях.

**Вердикт дизайнера:** 4/10. Токены есть, но использованы поверхностно, а брендинга нет.

### 3.3 Как пользователь

**Первое знакомство:**
- Открыл — заставка 400+600ms. Ок.
- Внутри — 2 демо-привычки. Ок.
- Нажал `+` — открылась форма. Тут issue #21: тип "количественная" выбрать нельзя, при редактировании открывается страница цвета, а не то, что нужно.
- Прошёл дальше через boolean-привычку. Создал.
- Ждал напоминания в 9:00 — не пришло (issue #13).
- Перешёл в статистику — увидел много цифр, но нет графика прогресса для конкретной привычки (issue #15).
- Забыл выполнить 2 дня, серия обнулилась. Захотел пометить "болел" — нельзя (issue #18).

**Что раздражает:**
- Меню "Завершить/Редактировать/Удалить" открывается долгим нажатием без подсказки. Открыть → закрыть можно только повторным долгим нажатием (issue #11).
- При редактировании часть шагов теряется (issue #21).
- 12 привычек в списке — экран длинный, компактного вида нет (issue #10).
- Прогресс за день считается от общего количества привычек, а если у меня привычка "3 раза в неделю" — она в остальные дни всё равно тянет процент вниз.

**Что понравилось бы, если было:**
- Утренние push-и — "3 привычки на сегодня".
- Разноцветные карточки — уже есть, приятно.
- Кнопка "Как я себя чувствую" (issue #19).
- Сводка "За неделю сделал 18 из 25" в конце воскресенья (issue #20).

**Вердикт пользователя:** 3/10 — задумка нравится, но реализация мешает.

**Вердикт разработчика:** 4/10. Работает как MVP, но production-ready требует ~10 недель.

## 4. Дорожная карта — 5 спринтов

Каждый спринт — 1–2 недели работы (в терминах агента: 1 длинная сессия + review). Спринты идут строго по порядку — каждый следующий опирается на инварианты, установленные в предыдущем.

### Спринт 1 — Стабилизация и критические баги (2 недели)

**Цель:** приложение не падает, уведомления работают, база под будущие фичи готова.

**Что входит:**
- Все 18 багов из таблицы выше (B1–B18).
- Issue #11 — меню действий на карточке закрывается по тапу вне.
- Issue #13 — уведомления.
- Ввод TypeScript-конфига (миграция начинается, но не обязательно на этом спринте закончена — сначала `.d.ts` для доменных типов и `checkJs: true`).
- Единый модуль `completion` — API-абстракция над тремя схемами.
- Миграция файлов в `src/` c подпапками.
- Удаление `HomeScreen.js` и `settingsStorage.js`.
- ESLint / Prettier переименовать → работает `npm run lint`.
- Error boundary + логгер (замена `console.log`).
- Sentry (или бесплатный аналог) — опционально.
- Плейсхолдеры `app.json` заменить на реальные.

**Definition of Done:**
- `npx expo start` без warnings.
- `npm run lint` — 0 ошибок.
- Ручной прогон: создать привычку → уведомление приходит в назначенное время (проверено на реальном Android).
- Меню действий на карточке закрывается по тапу вне.
- Все обращения к completions идут через один helper.

**Промпт:** `docs/prompts/sprint-1-stabilization.md`.

### Спринт 2 — Форма привычки и гибкость расписания (1.5 недели)

**Цель:** пользователь может создать любую привычку без затыков, план учитывает выбранные дни недели.

**Что входит:**
- Issue #21 — окно создания привычки:
  - выбор типа количественной привычки (unit, targetValue),
  - при редактировании открывать нужную страницу (цвет, категория, иконка) там, где начинал,
  - шаг 1: тип; шаг 2: имя/иконка/цвет; шаг 3: цель; шаг 4: расписание.
- Issue #17 — дни недели: массив 0..6, план считается от `targetDaysPerWeek` **на выбранных днях**, не от общего числа дней в периоде.
- Issue #16 — срок привычки: `endDate: null | ISO`, отображение остатка, автоархивация по истечении.
- Issue #14 — при редактировании статистики значения по умолчанию = план (не текущее значение, если оно 0).

**Definition of Done:**
- Все три типа привычек создаются и редактируются без ошибок.
- В статистике дневного прогресса привычки "3 раза в неделю в пн/ср/пт" не считаются на вт/чт/сб/вс.
- Привычка с `endDate` показывает "осталось 12 дней", по истечении переезжает в архив автоматом.
- В форме редактирования completions значения полей заполнены плановыми, если факт = 0.

**Промпт:** `docs/prompts/sprint-2-habit-form.md`.

### Спринт 3 — Статистика, графики и прогрессии веса (2 недели)

**Цель:** пользователь видит красивые графики и понимает свой прогресс по весу.

**Что входит:**
- Issue #15 — недельный и месячный график **для конкретной привычки** (сейчас есть только общий по всем).
  - Столбчатый график факт vs план.
  - Heatmap для boolean-привычки.
  - Line chart для веса.
- Issue #12 — прогрессии набора и снижения веса:
  - `weightGoal: 'lose' | 'gain' | 'maintain'`,
  - `startWeight` + `targetWeight`,
  - прогресс = линейная интерполяция между стартовым и целевым,
  - визуальный трекер: "осталось 3 кг".
- Рефакторинг Week/Month/Year статистики: вынести shared-логику в `useHabitStats(period)`.
- Компонент `<HabitChart habit period />` — переиспользуемый.
- Сравнение периодов: "эта неделя" vs "прошлая неделя".

**Definition of Done:**
- В карточке привычки при тапе на статистику открывается детальный экран с графиком.
- Weight goal `lose` показывает падающую линию к цели.
- Weight goal `gain` — растущую.
- Файлы Week/Month/YearStatistics сокращены минимум на 50% (было ~177 KB — стало ≤85 KB).
- Все графики отрисовываются через `react-native-svg` — уже есть в зависимостях.

**Промпт:** `docs/prompts/sprint-3-stats-charts.md`.

### Спринт 4 — Дневник дня: болезнь, голосовые/текстовые заметки, сводки (1.5 недели)

**Цель:** приложение перестаёт быть "чек-листом" и становится дневником.

**Что входит:**
- Issue #18 — больничный/отпуск:
  - тип `dayState: 'normal' | 'sick' | 'vacation' | 'skipped'`,
  - `sick`/`vacation` **не ломают серию** (streak считает такие дни как пропуск без штрафа),
  - визуально помечаются в календаре/heatmap.
- Issue #19 — описание дня:
  - текстовое поле (max 500 симв),
  - голосовая запись через `expo-audio`, локальное хранение,
  - transcription — опционально (за отдельным экраном "расшифровать", через сторонний API — задача Sprint 6+).
- Issue #20 — что сделал/посмотрел за день:
  - события дня: тип, название, оценка 1–10, заметка,
  - примеры: "кафе X — 8/10", "фильм Y — 5/10", "тренировка — 9/10",
  - сводка неделя/месяц/год: топ мест / фильмов / оценки по категориям.

**Definition of Done:**
- В карточке дня есть кнопки "я болел" / "отпуск" — серия не ломается.

## 6. Лог 5 циклов доработки плана

Ниже — как план менялся между итерациями, чтобы прийти к 10/10.

### Цикл 1 — первый черновик

Было: 5 спринтов по темам (баги, форма, статы, дневник, полировка). Проблема — Спринт 3 требует `startWeight`, а вводится он в Спринте 2. Спринт 4 требует чистого `streak`-контракта, а сейчас `getStreak` есть в utils.

### Цикл 2 — зависимости между спринтами

Перепроверил порядок:
- **Спринт 1** должен установить контракты, на которые опираются все следующие: единый `completion`-API, единый `streak`-API, timezone-safe даты.
- **Спринт 2** вводит поля `activeDays`, `endDate`, `startWeight` в схему привычки — все спринты 3–4 их будут читать.
- **Спринт 3** трогает `startWeight` и графики; ничего не ломает для Спринта 4.
- **Спринт 4** добавляет `dayState`; корректирует `streak`-API так, чтобы sick/vacation не ломали серию.
- **Спринт 5** ничего в контрактах не меняет — только UX.

**Изменение:** в Спринт 1 добавлено "единый completion-API" и "streak с расширяемым концептом skip". В Спринт 4 — только реализация конкретных состояний.

### Цикл 3 — перспектива пользователя (что видно в конце каждого спринта)

Смотрю, в конце каждого спринта пользователь должен увидеть **осязаемую** победу:
- После **S1** — "приложение больше не глючит, уведомления пришли". ✅
- После **S2** — "я наконец создал привычку без затыков, план учитывает мои дни". ✅
- После **S3** — "я вижу график своего прогресса и как убывает вес". ✅
- После **S4** — "я записал голосом что было в четверг, и в воскресенье увидел сводку". ✅
- После **S5** — "выглядит как настоящий продукт". ✅

**Изменение:** в S1 добавлено "уведомление приходит" в DoD как обязательное — иначе спринт "невидим".

### Цикл 4 — перспектива разработчика (гранулярность и тестируемость)

Проверил: каждая задача должна быть:
- **Атомарной** — можно сделать за <4 часа.
- **Тестируемой** — есть чёткий критерий приёмки.
- **Изолированной** — не требует правки соседних областей.

**Изменения:**
- В Спринт 1 добавил вынос всего в `src/` первой задачей, чтобы все дальнейшие правки шли уже по новой структуре.
- В Спринт 3 добавил рефакторинг Week/Month/YearStatistics **до** добавления графиков — иначе новые фичи размажутся по 177 KB.
- В Спринт 4 разделил "голос" и "текст" — текст в MVP спринта, голос как отдельная задача.
- В Спринт 5 unit-тесты покрывают только чистые функции (не UI), чтобы уложиться в 2 недели.

### Цикл 5 — проверка полноты

Что могло быть упущено:
- Cloud sync / multi-device → **вне scope** (одно устройство первым релизом).
- Локализация → **вне scope** (RU only).
- iOS билд → app.json подготовлен, но тестирование только Android (совпадает с задумкой пользователя).
- Backup/export → **вошло в S5** (Export/Import JSON).
- Privacy / GDPR → добавлено в S5 (privacy screen, all-local-data disclosure).
- Web/Expo web → **не поддерживаем**, оставим как есть.
- Analytics → вне scope (privacy-first).
- Achievement notifications — правильно работают только когда достижения не закомментированы. Включено в S1 (B5).

**Финальные добавления:**
- В **S1** — миграция схемы (`storage.version = 1`), чтобы S2 мог свободно менять поля.
- В **S5** — privacy-экран и disclaimer, JSON export/import, README с checklist для Play Store.

План считаю финальным.

## 7. Как использовать промпты

Для каждого спринта — свой файл в `docs/prompts/sprint-N-*.md`. Промпт полностью самодостаточен: содержит контекст проекта, задачу, критерии приёмки, файлы к правкам, порядок действий.

1. Открой соответствующий промпт.
2. Скопируй **всё содержимое** в новую сессию любого AI-агента (Claude Code, Cursor, etc.).
3. Убедись, что AI имеет доступ к репозиторию.
4. Отдай команду "выполни спринт".
5. По завершении — проверь `Definition of Done` из промпта.

Спринты **строго последовательны** — не запускай Спринт N+1, пока N не закрыт полностью, иначе поедут инварианты.
